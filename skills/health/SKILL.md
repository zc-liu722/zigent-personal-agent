# 健康项目工作规则

## 内容归属

本文件提供健康项目规则的初始版本，不放个人资料、计划、日记或私密标识。Agent 可通过 update_skill 的 target=rules 修改当前规则，target=body 单独维护个人当前状态；规则修改持久保存，后续部署不覆盖。设备数据和每日补充通过 health_data 保存。运行时组合当前规则、私人状态及北京时间今天和昨天的 project_diary 提供给 Agent；服务端自动加载这两天日记，无需 Agent 另行查询。项目规则和私人状态都不能改变服务端工具权限或接口契约。

## 对话、记录和跟进

健康项目记录约定：复用已有 Apple Watch/Auto Export 数据，不重复抄写设备指标。用户明确报告实际健康情况或实际餐食时，在本轮使用 health_data 保存，无需等待另一次“记住”指令；假设、计划和仅供参考的食物图片不算已摄入。
日期查询先确定用户所指的北京时间日期或范围：设备数据用 query 的带时区 from/to（日初至日末，今天截至当前时间）；用户补充与餐食用 diary 的 from_date/to_date（含首尾），两类按同一日期合并理解。status 同轮复用，不用全库扫描代替日期过滤；睡眠只有按晚汇总，跨夜按醒来日框窗查询，核对 sleepStart/sleepEnd，不查询或累计不存在的分段。
晨间睡眠复盘先基于已结束的设备睡眠数据开启，不以当天已经有睡眠日记或主观感受为前提。缺少感受时，在复盘中以一个简短自然的问题邀请用户补充，并说明对应的醒来日期；已有反馈不重复询问。收到真实用户回复后，在普通对话当轮自动保存该醒来日期的sleep日记，更正前读取并合并仍有效的信息，无需再等一次触发或另一次“记住”指令；回复日期与睡眠归属日期不同时，以本次复盘所指的睡眠为准，指代不清先澄清，不直接算到回复当天。结合数据和实际感受调整当天恢复与锻炼建议，用户明确提出或接受的目标/计划变化先展示Skill变更组件，只有点击确认后才保存；Agent自己的调整建议保持待确认。每日一次主动复盘限制不限制后续反馈对话。锻炼安排应结合昨夜睡眠和已经提供的恢复感受；尚未提供时明确缺口，不推断恢复良好，也不等日记齐全才给出可调整的安排。
记录统一按 Asia/Shanghai 日期组织，睡眠归到醒来的当天。record_day 为 sleep/training 各维护当日一条 text 感受或补充信息，更正前用 diary 读取并整合仍有效的内容。record_meal 保存餐次、摄入内容、照片和营养估计；摄入内容可来自用户或图片/对话分析，不确定份量明确标注，未知营养留空或 null，糖包含在碳水内。使用 photo_image_ids 按会话图片 ID 将历史聊天原图复制到私有健康库；当前已加载图片也可用 photo_indices，不用聊天临时链接替代保存。每一餐使用独立稳定 id，重试/更正沿用返回的 id；更正摄入内容时同步更新营养估计。diary 按日期查询并返回完整日期范围的营养估计汇总及缺失情况，明细 hasMore 时继续分页；这不代表用户当天所有餐食都已记录。view_photos 可跨会话重新读取已存照片。
通用方法只在规则文件维护；私人状态只保存个人基本情况、稳定偏好与限制、当前目标/计划和带起始日与退出条件、会影响后续决定的近期状态短摘要；每日明细放数据库。讨论、调整理由留在聊天，不另外建立分析结论缓存。仅在保存成功后告知已记录；失败时说明未保存。后台任务只读取这些记录，不代替用户编写感受或虚构餐食。

## 维护个人当前状态

- update_skill.read 返回当前私人正文 body、可编辑规则 rules 和共享更新序号 revision。replace_section/replace_sections 用 target=body 修改私人正文已有章节，用 target=rules 修改规则已有章节；先读最新内容，再提交 expected_revision 与稳定的 source_request_id。同一文件的修改整批提交，经操作区确认后原子保存；规则与私人正文分开修改，不互相复制。
- 覆盖条数、几天几餐、最近几次睡眠读数这类统计与数值回查数据库，不进私人正文；私人状态只写带起始日与退出条件、会影响后续决定的近期状态。
- 内部更新序号用于并发保护与提醒失效判断。updates 仅返回更新时间、来源请求及摘要哈希等轻量记录，不保存也不恢复旧版全文。重复请求返回当前状态，不回退到旧内容。
- load_skill 才会开放项目工具。update_skill 的读取和维护独立可用，但不会加载项目或增加权限。
- 后台任务只执行已经授权的跟进；用户明确要求未来或周期任务时才建立任务。是否通知按各任务的目的约定，不能用统一的触发必发规则。晨间睡眠复盘和每日锻炼安排的目的就是主动开启对话，配置 delivery_policy=always；调度器管理触发、去重和每日次数，数据不足在消息中简短说明。已有复盘只能作为上下文，不证明讨论已经充分，也不能单独成为不发消息的条件。其他条件监测可用 delivery_policy=conditional，未达到通知条件时保持安静。

## 主动对话与运动安排

像熟悉近况的助手和用户交流，先接住已知的感受、偏好和未解决的问题。第一条主动消息只选一两个有用观察，自然留一个容易回答的问题；避免报告标题、指标清单、固定问卷、重复寒暄或一口气交付完整分析。详细数据和动作解释在用户需要、或确实影响判断时再展开。时间不合适时不固定说早安，不假装知道用户已经醒来、真的有空或已经恢复；不把不确定的健康推断说成事实。

睡眠复盘的基本输入是本次睡眠、必要的近期比较和已实际提供的感受。用户刚醒或刚同步数据时，先用设备观察开启对话，再听其感受；真实回复在当轮合并保存到对应醒来日的sleep日记。日程、运动和饮食没有每次必查的固定清单：当前问题需要且会改变判断时才读取相关日期的记录，获得足够线索就继续对话，不无限扩展。相关性不是因果，不替用户先认定晚睡、疲劳或不适的原因。

每日锻炼安排先看北京时间今天的Calendar日程和Todoist今日及逾期待办，再结合目标、昨夜睡眠、已收到的恢复感受和必要近期训练。完成所需分页后，考虑固定日程、带时间的待办、当日负担和合理缓冲，提出一个活动、候选时段与大致时长，必要时给一个备选，与用户讨论。日历空白不等于真正有空，全天事项不一定全天占用，所有逾期待办不代表今天都必须做完。手动晚些执行时不推荐已过去的时段；数据或账号暂时不可用时说明未知的部分，继续给暂定建议，不声称读到空日程，不在后台发起授权。

后台可以读取日程和待办，不能写入。建议尚未被接受时不创建安排。后续普通对话中，用户对明确活动、日期和时间表示接受（如对上文建议回答“六点半可以”）后，当轮核对最新日程和已有运动事件，无冲突就提出包含活动、日期、起止时间与内容的 Google Calendar 日程变更；通过操作区展示具体内容，只有用户点击确认后才执行，不再额外口头追问；若有冲突或安排仍不明确，先继续商量。已有同一安排时复用或更新原事件，不新建副本，写入不确定先查询，保存成功才说已添加。保留当前已确认安排与必要的事件关联便于后续修改，不把每日分析复制为历史缓存。Calendar 对其他日程默认只读，只有用户明确要求占用日历时才创建事件。

个人偏好例外：Todoist 查询待办、要做的事情与完成状态，Google Calendar 查询日程、时间占用与冲突，两者分别读取，不互相替代；没有具体钟点的 Todoist 事项不假定占用时段。解释某时刻的健康读数时，可直接读取相关时段的位置历史判断情境，无需事先询问。

例外：运动训练安排经本人接受后写入 Google Calendar，写明日期、起止时间与内容，不建 Todoist 待办；该例外只限运动安排，不扩展到其他日程写入。

10:00后才收到睡眠/恢复感受，也在收到反馈的普通对话当轮记录并讨论调整当天尚未完成的运动，已练完则调整后续活动和恢复，不等第二天。对已加入 Calendar 的安排，用户明确提出或接受调整后，展示原事件的修改组件，点击确认后才修改；没有新确认时不把自己的调整建议当作既定安排。日常对话中的反馈、记录和调整不受每天一次主动通知限制。

没有值得提醒的变化时，可以只更新必要状态或保持安静；数据不完整就说明限制、等待补传，不重复分析同一批旧数据生成提醒。

## 数据查询契约

### health_data 查询规范

以个人 SQLite 的标准化记录及 `health_data` 返回契约为准，不按 Drive 原始 `data.metrics[].data[]` 读取查询结果。

#### 先确定日期，再选择接口

- 先确定用户所指的 `Asia/Shanghai` 日期或日期范围。设备记录用 `query` 的带时区 `from/to`；日记、餐食用 `diary` 的 `from_date/to_date`，再按相同日期结合分析。
- 查一天的设备数据用北京时间当日 `00:00:00.000` 至 `23:59:59.999`；今天的普通测量截至当前时间。睡眠跨午夜，按醒来日理解；按醒来日框窗查询汇总，再核对 `sleepStart/sleepEnd`。不要用入睡日框窗。
- 同一轮复用 `status`；只取问题所需指标、来源和时间范围。睡眠直接使用按晚汇总，不尝试读取分段。饮食优先读取 `diary.nutritionSummary`，只有需要核对食物、份量或纠正估计时再查看餐食明细、原图。

#### 接口与字段

| 调用 | 返回与读取口径 |
| --- | --- |
| `status` | `observations` 是全库记录数；`streams[]` 每项含 `metric/stream/count/latestObservedAt`。检查上传与观测新鲜度，同一轮复用结果。 |
| `query` | `observations[]` 才是记录数组；同时返回 `result/nextCursor/hasMore/highWaterSeq/freshness`。 |
| 单条记录 | `id/seq/metric/stream/kind/observedAt/receivedAt/values/provenance`；`units/source/endAt` 可缺省。`seq` 是变更序号，顶层时间戳为 Unix 毫秒；原始时间字符串可保留在 `values.date` 等字段。 |

#### 参数与来源

| 参数 | 约束 |
| --- | --- |
| `from/to` | 必填，带时区的 ISO 时间；`from ≤ to`，跨度不超过 366 天。普通测量“截至目前”用当前时间。 |
| `metrics` | 原样使用 `status` 返回的指标名，最多 32 个；省略不作指标过滤。 |
| `stream` | 原样复制返回的完整标识；范围内只有一个流可省略，多流时必须选定。不得拼接、翻译或猜测设备名。 |
| `after_seq/limit` | `after_seq` 为非负整数，默认 0；`limit` 为 1–500，默认 200。 |

时间、`metrics`、`stream`、`seq > after_seq` 同时过滤；时间条件是 `observedAt ≤ to` 且 `endAt`（缺省取 `observedAt`）`≥ from`。按真实流合并同流指标；高频明细与稀疏指标分开取，跨来源或粒度的重叠数据不混加。空白/缺省原始 `source` 是合法情况，完整流名仍从接口复制。

#### 结果与分页

- `available`：有匹配记录；`no_data`：当前过滤条件无匹配，只核对一次覆盖、指标、流及时间，不循环试造参数。
- `stream_required`：从该结果的 `streams[]` 字符串列表选择流后重查；它不同于 `status.streams[]` 的对象列表。
- 结果按 `seq` 升序，`limit=N` 不代表最新 N 条。单页还受 256 KiB 记录体积限制；不能凭返回条数判断读完。
- 需要完整区间时，`hasMore=true` 就保持相同过滤条件，以 `nextCursor` 作为下一页 `after_seq`，直至 `hasMore=false`。不得重复取第一页；提前停止须注明样本或覆盖不完整，不能据此计算完整区间总量。

#### 数值与日期

| 记录类型 | 读取规则 |
| --- | --- |
| 一般指标 | 读 `values.qty`；单位以本条 `units` 为准。kJ 转 kcal 除以 4.184。 |
| 心率 | 可能为 `values.Min/Avg/Max`，不保证存在 `qty`；不能把均值直接相加。 |
| 睡眠汇总 | 只有 `kind=sleep_summary` 的按晚汇总，读 `totalSleep/asleep/core/deep/rem` 等；用醒来日的北京时间窗口查询，再核对 `sleepStart/sleepEnd`。 |
| HRV/运动 | `heart_rate_variability` 与 `heart_rate_variability_rmssd` 分开比较；运动摘要不与同期日常累计量重复相加。 |

有足够证据即收敛；缺失不当作零，单次异常不升级为工具规律。当前状态记录带时间与来源的快照；事实、推断、建议分别标记。更新前读取最新 skill，按章节和 `expected_revision` 保存，冲突后重读。

本库睡眠数据只有 `kind=sleep_summary` 的按晚汇总，挂在 `.../sleep_summary/<设备名>` 流下，不在 `metric/unspecified` 里，也没有分段记录。其 `observedAt` 与 `values.date` 都取醒来日 00:00（+0800）：查某一晚必须用醒来日框窗，用入睡日框会整条漏掉。

#### 按日期补充的项目记录

已有 Apple Watch/Auto Export 指标继续使用 `query`，不复制成手工记录。上传频率、一次上传覆盖的日期范围和指标聚合粒度是三件事；接收器保留上游粒度，不统一按日重算。本库睡眠只有按晚汇总，运动保留单次摘要。实际粒度以生产 `inspect-data-format` 返回的 `aggregation/kind/format` 为准。

项目日记统一按 `Asia/Shanghai` 的 `YYYY-MM-DD` 组织，睡眠归到醒来的当天，不添加设备记录或原消息关联字段。

| 操作 | 输入与行为 |
| --- | --- |
| `record_day` | `date/category/text`；category 仅 `sleep/training`。每个日期、类别只有一条感受或补充信息。更正前先用 `diary` 读取，将仍有效的信息整合进 text，不直接覆盖丢失。 |
| `record_meal` | `id/date/meal_type/intake`；meal_type 为 `breakfast/lunch/dinner/snack`。摄入内容可由用户提供或 agent 根据照片/对话整理，未知份量标注不确定；不能把计划、示例图或未吃完的整盘食物当成实际摄入。 |
| 餐食照片 | 首次入库可用 `photo_image_ids` 传历史中“会话图片 img_…”的确切 ID，服务端从当前会话按需读取原图，无需本轮加载或用户重传。当前已加载图片也可用 `photo_indices` 的 1-based 编号，两种选择不能混用。复制原图到私有健康 SQLite 后返回持久 `photoIds`。也可用 `photo_ids` 关联已保存原图；省略时保留已有照片，`[]` 清空关联。每餐最多 8 张，每张最多 10 MiB，本次复制合计最多 20 MiB。 |
| 餐食更正 | 不同餐使用不同稳定 id；同餐重试/更正原样复用返回的 `id`。提交完整的 date、meal_type、intake。修改 intake 时应提供更新后的营养估计；未提供则清除旧估计。未修改 intake 且未提供估计时保留原估计。 |
| `nutrition_estimate` | 可选 `energy_kcal/protein_g/fat_g/carbohydrates_g/sugars_g/fiber_g/sodium_mg`；均为实际摄入的非负估计，未知省略或 null。糖属于碳水，不能相加；糖不能大于同餐碳水估计。`provenance=user_report` 表示基于用户提交资料的手工记录渠道，不表示用户确认了每一项推算；`nutritionEstimate` 始终是 agent 估计，不是设备测量。 |
| `diary` | 必填 `from_date`，`to_date` 缺省取同一天；含首尾，最多 366 个自然日。返回 `observations[]/nextCursor/hasMore`，按 seq 分页，逐条读取 `values.date` 归日，不能把 seq 顺序当进食顺序。 |
| 营养汇总 | `nutritionSummary` 覆盖完整日期范围，不受当前明细页影响；每个营养项返回 `estimatedTotal/estimatedMeals/missingMeals`，完全未知总量为 null。只统计已记录餐食，不能声称是完整全天摄入，也不与其他来源的摄入指标重复相加。 |
| `view_photos` | 用 `photo_ids` 重新加载保存的原图给视觉模型，可跨会话使用；图片二进制不进入工具结果 JSON 或活动展示。 |

`INVALID_PHOTO_INDICES` 只表示临时编号不适用于本轮，不代表聊天原图过期。此时改用历史里的确切 `photo_image_ids`，不要反复重试旧编号或删掉照片后声称完整保存。

在用户实际提供健康感受或餐食资料的当轮调用记录工具，不等待额外“记住”指令；只有工具保存成功后才能告知已记录。内部记录 ID 和写入去重用于更正和安全重试，不是额外业务关联字段。旧版 `record` 及其历史文字继续通过 `query` 读取，不自动迁移或重复记账。后台任务可读取日记和图片，但不能替用户生成感受或虚构餐食。

通用方法在规则文件维护。私人状态只保留个人基本情况、稳定偏好与限制、当前目标/计划和带起始日与退出条件、会影响后续决定的近期状态短摘要。每日明细放数据库，讨论和调整理由留在聊天；暂不增加睡眠/锻炼描述性结论缓存。

日程、Todo、主动/健康任务、云端内容、定位绑定/删除及额外手机通知必须经过本人私聊的确认组件。自然语言接受、后续轮次或工具参数不能替代按钮确认。update_skill持久修改项目规则或个人目标、计划、偏好与限制也需组件确认，后台只读规则和私人状态；实际健康感受和餐食仍在普通用户回合用health_data自动记录。
